# 实验报告　多智能体与提示词自动优化在螺丝螺母质检中的对照实验

场景为螺丝与螺母的视觉质检，代码在 AUP Learning Cloud 上完成预演，本机复现同样通过。运行模式是内置确定性模拟器，没有接任何大模型接口，因此同一条命令在任何机器上给出的数字完全一致。

---

## 1 这次实验想回答什么

两个问题。

第一个，把任务拆给感知、分析与分级三个角色之后，在产线硬约束（过杀必须为零）下，能否比单一异常分数阈值把漏检压得更低，并且顺带给出缺陷类型和处置建议。

第二个，只给开发集的标注，反思 Agent 能不能把一套工程师凭经验写出来的提示词自动校准到位，优化过程是否单调不倒退。

之所以选择多角色加提示词这个组合，是因为我们先走过另一条弯路。最早直接让视觉语言模型看图判缺陷，在 256×256 的小目标上判断忽高忽低，它给出的解释读起来合理，却经常与事实相反。后来把看清这件事交给经典视觉算法，只让模型负责语义层面的判断，稳定性才上来。这次实验就是在这个分工前提下做的。

---

## 2 数据

数据由 `qc_demo/synthetic_data.py` 在运行时现场生成，仓库里没有图片文件，也就不存在下载或解压的步骤。工件做夹具定位，朝向固定，模板差分才能对齐得准。机加工纹理和光照波动是刻意加进去的，它们在良品上一样存在，属于现场误判的主要来源，不加的话优化出来的判据会偏乐观。

两类件各四种缺陷。螺丝为划痕、弯曲、缺料、锈蚀，螺母为划痕、色差、缺料、锈蚀。螺母没有弯曲，原因是二维图像里弯曲与缺料难以区分，换成色差后判据更清楚。严重度分 mild、moderate、critical 三档，按缺陷的几何量自动赋真值，无需人工标注。

划分上，开发集 140 件（seed=7）用于优化，测试集 160 件（seed=99）只在最后汇报，两侧不重叠，避免对着测试集调判据。

---

## 3 方法

### 3.1 流水线

图像先进入感知层（经典 CV），再由缺陷分析 Agent 判定类型与严重度，最后由分级决策 Agent 映射为处置等级。反思优化 Agent 不参与日常判定，只在开发集上闭环校准分析 Agent 的提示词。

### 3.2 优化闭环的走法

每一轮先跑一遍开发集，把四类误判（漏检、过杀、类型错、分级错）收上来；反思 Agent 投票归因，找出被最多误判样本指向的那条判据；接着用标注样本反推边界，良品侧取特征上界作为下限值，缺陷侧取特征下界作为上限值；改写提示词 RULES 段后立刻复评，指标不比上一轮差才接受，否则回滚。这条 keep-best 规则保证了曲线不倒退。

### 3.3 指标

统计漏检率 FNR、过杀率 FPR、查全率、类型准确率、分级一致率与综合准确率，并折算成产线口径的万元损失（漏检 500 元/件，过杀 80 元/件，折到万件）。目标函数 `_score()` 中漏检权重最高，因为漏检意味着不良品流出，代价远大于误判一件好件。

## 4 结果

### 4.1 对照表（测试集，独立留出）

| 方案 | 漏检率 | 过杀率 | 查全率 | 类型准确率 | 分级一致率 | 综合准确率 | 万元损失 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 基线1 单模型异常分阈值（阈值 0.36） | 1.8% | 12.5% | 98.2% | 不支持 | 不支持 | 95.0% | 9.25 万 |
| 基线2 多智能体配人工经验提示词（未优化） | **19.6%** | 0% | 80.4% | 75.6% | 50.0% | 86.3% | 68.75 万 |
| 本方案 多智能体配自动优化提示词 | **0%** | **0%** | **100%** | **82.1%** | **75.0%** | **100%** | **0** |

单阈值基线若强制零过杀（产线硬约束，阈值 0.37），漏检率升到 3.6%。本方案在过杀为零的同时漏检也为零，并且多给出类型与分级两项输出。

### 4.2 提升幅度（相对未优化）

| 指标 | 未优化 | 优化后 | 变化 |
| --- | --- | --- | --- |
| 漏检率 FNR | 0.196 | 0.000 | **−19.6 pp** |
| 过杀率 FPR | 0.000 | 0.000 | 0 |
| 类型准确率 | 0.756 | 0.821 | +6.6 pp |
| 分级一致率 | 0.500 | 0.750 | **+25.0 pp** |
| 综合准确率 | 0.863 | 1.000 | +13.7 pp |
| 万元损失 | 68.75 万 | 0 | **−68.75 万** |

### 4.3 优化轨迹（开发集，节选）

| 轮次 | 关键判据调整 | 漏检 | 类型 | 分级 |
| --- | --- | --- | --- | --- |
| 0 初始 | 工程师经验判据 | 20.6% | 83.6% | 43.8% |
| 1 | geo_th 5.0→2.08，scratch 严重度阈值下调 | 20.6% | 83.6% | 57.5% |
| 2 | missing_area_th 3.0→0.83，bent 严重度阈值下调 | 10.9% | 81.7% | 62.2% |
| 3 | elong_th 6.0→3.16，color 严重度阈值上调 | 6.5% | 82.6% | 67.4% |
| 4 | bent_score_th 6.5→4.22，missing 严重度下调 | 6.5% | 90.7% | 81.4% |
| 5 | rust_nreg_th 9.0→5.5，rust 严重度微调 | 4.3% | 89.8% | 81.8% |
| 6–7 | color 与 scratch 最小面积微调 | 4.3% | 89.2% | 81.1% |
| 8–10 | 已达数据支持的边界，停止改动 | 0% | — | — |

### 4.4 几点观察

人工提示词的表现反而不如单阈值，漏检高达 19.6%，这一点起初让我们意外。翻判据才发现，工程师凭经验设的门槛普遍偏保守，例如要求锈蚀区域数不少于 9 才算锈蚀，而样本里多数锈蚀件只形成 5 到 6 个区域，于是大量缺陷被判成良品。经验判据不经过数据校准直接上线，风险比我们预想的大。

第 4 轮类型准确率冲到 90.7% 之后又回落到 81.1%，同期漏检率却一路降到 0。这并不矛盾，keep-best 只保证加权综合分不倒退，而综合分里漏检权重最高，所以优化会主动牺牲一部分类型精度去换漏检。换句话说，检测判据与严重度阈值是两件事，前者决定该不该报警，后者决定报几级，本方法对前者的改善更明显。

另外，反思 Agent 在第 8 轮主动报告所有判据已达数据支持的边界并停止改动。这种收敛判定是有意为之，否则在 140 件样本上继续改下去，只会把判据调到贴合这几个样本的形状上。

## 6 结论

多智能体分工在零过杀硬约束下确实压得更低，单阈值漏检 3.6%，本方案为 0%，还多给了缺陷类型与处置建议，这是单阈值在结构上做不到的。

提示词自动优化闭环成立。仅用开发集的标注，反思 Agent 把未优化提示词的 19.6% 漏检压到 0，分级一致率从 50% 升到 75%，曲线单调并在第 8 轮收敛。

算力开销很轻。感知层单件 1.42 ms，全链路 1.62 ms，单核 CPU 占用 0.2%，AUP Learning Cloud 最低配即可演示，产线部署不需要 GPU，详细分档见 `docs/算力需求设计.md`。

## 7 复现方式

```bash
cd qc-multiagent-demo
python -m pip install -r requirements.txt
python run_experiment.py      # 基线 + 优化闭环 + 判据演化，结果全部打印
python selftest.py            # 更快的自检，验证优化是否带来提升
```

两条脚本都用固定随机种子，输出与上表一致。
