# 面向精密紧固件缺陷检测的多智能体协同与提示词自动优化系统

## ——基于 AMD AUP Learning Cloud 的工程实践报告

**报名题目（B 自命题型）　** 基于多智能体与提示词自动优化的工业视觉质检系统设计与云端预演

---

## 摘要

工业质检有个矛盾，模型能力足够，但判据由工程师凭经验写进提示词，换产线就要重调，且说不清为什么。本实践以螺丝、螺母为对象，构建缺陷分析、分级决策、反思优化三个 Agent 组成的质检系统，把判据写成提示词中可读可改的规则段，由反思 Agent 依误判反推边界、自动迭代。系统在 AMD AUP Learning Cloud 完成预演，以自带真值的合成缺陷图像为数据，140 件开发集优化、160 件独立测试集评估，漏检率由 19.6% 降至 0，分级一致率由 50.0% 升至 75.0%，万元损失归零，全链路单件 1.62 ms、单核占用约 0.2%。

**关键词　** 多智能体；提示词自动优化；工业视觉质检；异常检测；AUP Learning Cloud

## 一、选题背景与问题定义

精密紧固件是装配基础件，表面划痕、杆部弯曲、螺纹缺料、锈蚀一旦流入下游，轻则装配干涉，重则整机召回。人工目检强度高、一致性差，视觉替代势在必行，但落地有三难。

其一，缺陷样本稀缺。产线不良率常在千分之几，收集数百张缺陷样本往往耗时数月，监督学习难以起步。其二，判据依赖工艺知识且随产线漂移。同类划痕在光面件上超过 0.3 mm 即判不良，在带纹理的件上可放宽到 0.5 mm；这种经验难写成通用代码，却恰好可用自然语言描述。其三，决策不止好/坏，产线还需知道缺陷类型、严重程度与处理建议，单一分数给不出。

大模型擅长后两件事，却不擅长前一件——让视觉语言模型直接判小缺陷，稳定性不足且会给出看似合理的错误解释。本实践据此确立三层分工，**经典视觉算法承担像素级的异常检出，智能体承担语义层面的类型判定与处置决策，反思机制则依据误判样本持续校准判据**。

## 二、Proposal 规划

### 2.1 目标与范围

交付一个可在云端一键预演的小型系统，输入一件紧固件图像，输出异常判定、缺陷类型、严重度等级与处理建议，并能在少量标注样本驱动下自动改进判据。

### 2.2 架构与技术路线

系统分三层。**感知层**以经典视觉替代重型模型，由 9 张良品图像取中值合成模板，与待检图像差分（阈值 18）后经闭运算、连通域分析，提取异常面积占比、可疑区域数、最大面积、最大细长比、几何畸变度、面积偏差、长宽比偏差、实心度偏差等 8 维特征。不用 PatchCore 一类方法，是刻意权衡，紧固件由夹具定位、朝向固定，模板对齐稳定；经典视觉单件仅毫秒级，无 GPU 即可预演。

**决策层**由三个智能体构成，缺陷分析 Agent 按规则树判定类型与严重度并给出理由；分级决策 Agent 将严重度映射为处理等级，并带硬约束兜底防止越界；反思优化 Agent 不参与日常判定，只在离线阶段统计误判、判断哪条判据投错了票，再依标注样本反推边界、改写提示词。

**优化闭环**是核心。提示词采用自然语言说明 + 机器可解析 RULES 段的混合结构，每条判据是形如 `geo_th=5.0` 的键值对，人可读、程序可精确替换。每轮先做误判归因投票，对漏检样本，向构成该缺陷判定条件的每条判据各记一票；分级错误按缺陷类型投票。得票最高者被改写，新值由标注样本反推（良品侧最大值乘系数作下限，缺陷侧最小值乘系数作上限，取交）。改写后立即在开发集复评，**指标不变差才接受，否则回滚**（keep-best），保证曲线单调不倒退。

### 2.3 数据策略

合成数据是刻意设计。生成器按类型与严重度两个维度参数化造缺陷，并叠加机加工纹理与光照抖动——二者在良品上同样存在，正是现场误判主因，必须注入，否则优化出的判据在真实场景中会过于乐观；真值随图生成。真实数据沿用同一接口，将 MVTec AD 的 `metal_nut`、`screw` 按同一结构组织，替换加载器即可，感知层与智能体层无需改动。

## 三、系统实现

### 3.1 感知层

感知输出不止热力图，而是一组可解释的几何量，判缺料看几何畸变与面积偏差，判划痕看细长比与面积，判锈蚀看区域个数——这些量与工艺人员的描述方式对应，为把判据写进提示词提供了语言基础。

### 3.2 决策层

RULES 段本质是一棵有序判定树，先看锈蚀（区域数超阈值），再看弯曲（螺丝且异常分超阈值），再看缺料（几何畸变与面积偏差同时超标），再看划痕（细长比与面积同时达标），最后看色差，皆不满足判良品。把判定顺序写进提示词，是为让为什么这样判可追溯，这是工业场景的硬性要求。分级 Agent 另设硬约束，模型等级与严重度映射表冲突时以映射表为准，以可审计为底线。

### 3.3 优化闭环

完整过程可概括为归因—反推—验证—回滚。实际一轮中，`geo_th=5.0` 被判定为 9 例误判元凶，反推新边界 2.08，改写后开发集漏检率由 20.6% 降至 10.9%；下一轮 `missing_area_th` 由 3.0 收紧到 0.83，漏检率再降至 6.5%。优化在第 8 轮收敛，此时反思 Agent 报告所有判据已达数据支持的最优边界，主动停止，避免在有限样本上继续过拟合。

### 3.4 工程形态

大模型调用封装为可插拔客户端，配置 OpenAI 兼容接口即走真实模型，否则启用内置确定性模拟器。模拟器并非假数据，它严格按 RULES 段执行判定，提示词改了什么、效果变没变都能真实反映，使项目在无密钥、无 GPU 环境仍可复现优化过程。界面分三个页签，单件抽检、提示词自动优化与对照实验；针对优化前后提示词看似一样的观感，另加判据变更对比表列出前值与后值。

## 四、云端预演

### 4.1 环境与部署

预演在 AMD AUP Learning Cloud（`tpe.aupcloud.io`）完成。平台为 JupyterHub 形态，登录后在启动页选环境镜像，本项目纯 CPU 即可，故选 CPU 类环境（Code Server）以免占 GPU 配额；进入后由集成终端部署，压缩包上传、Python 标准库解压、装依赖、启动服务，经平台端口转发访问。

### 4.2 预演中的四个问题

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 按本机路径 `cd` 报不存在 | 云端为独立 Linux 容器，无 `C:` 盘 | 打包上传后解压，用相对路径 |
| 解压报 `unzip: command not found` | 镜像未装 unzip | 改用 `python -m zipfile` |
| 组件全部报错、提示 `Unexpected token '<'` | 代理剥离子路径，前端仍按根路径请求 | 启动时设 `GRADIO_ROOT_PATH` 为完整代理地址 |
| 装依赖报 `from versions: none` | 国内镜像返回空候选 | 改用官方 PyPI |

第三个问题最具代表性，框架能打开、组件全报错，本质是代理子路径与前端认知不一致，属部署期集成缺陷，与算法无关。

### 4.3 预演结论

全链路走通，优化过程可实时观察，验证了可演示性与可复现性；全程无需 GPU、外部数据集与密钥。

## 六、实验结果与分析

### 6.1 设计

三条对照线，**基线一**为单模型异常分数阈值法，阈值在开发集按漏检最优选取、测试集汇报，并给出强制零过杀口径；**基线二**为多智能体配人工经验提示词；**方法**为多智能体配自动优化提示词。数据严格隔离，140 件开发集用于优化，160 件独立测试集仅作最终评估，种子固定，一条命令即可复现。

### 6.2 结果

| 方案 | 漏检率 | 过杀率 | 类型准确率 | 分级一致率 | 综合准确率 | 万元损失 |
| --- | --- | --- | --- | --- | --- | --- |
| 基线一（dev 选阈值） | 1.79% | 12.50% | 不支持 | 不支持 | 95.0% | 9.25 万元 |
| 基线一（强制零过杀） | 3.57% | 0 | 不支持 | 不支持 | — | — |
| 基线二（人工提示词） | 19.6% | 0 | 75.6% | 50.0% | 86.3% | 68.75 万元 |
| 本方法（自动优化） | **0** | **0** | **82.1%** | **75.0%** | **100%** | **0** |

三点值得说明。其一，人工提示词反而远差于单阈值，漏检率高达 19.6%——工程师凭经验设的门槛普遍偏保守（如要求锈蚀区域数不少于 9），大量缺陷被漏掉，说明经验判据未经数据校准就上线是危险的。其二，优化后漏检与过杀同时归零，且额外给出类型与分级，为单阈值结构上无法提供的能力。其三，优化只在开发集进行，测试集仍零漏检，说明改写的是可迁移边界而非记忆样本。

### 6.3 提升从何而来

优化共改写 13 条判据，漏检率呈阶梯下降 20.6%→10.9%→6.5%→4.3%→0，分级一致率 43.8%→57.5%→62.2%→67.4%→81.4%。两类改写性质不同，门槛类（如 `geo_th`、`elong_th`）修正该不该报警，属检测能力；严重度阈值（如 `sev_scratch_1` 由 480 降至 287）修正该报几级，属决策粒度。二者协同才是综合准确率从 86.3% 跃至 100% 的原因。

## 七、未来算力需求设计

### 7.1 实测基准

本机单核实测，感知层 1.42 ms/件，含两 Agent 的全链路 1.62 ms/件，等价吞吐约 617 件/秒，单核占用约 0.2%。可见当前形态的瓶颈不在算力，而在数据与判据。

### 7.2 分阶段方案

| 阶段 | 场景 | 建议配置 | 用途与依据 |
| --- | --- | --- | --- |
| 一阶 | 教学预演、方法验证 | 单核 CPU、2 GB 内存 | 实测 617 件/秒，够用 |
| 二阶 | 接入真实数据 | 1×GPU（16 GB 显存）、8 核 CPU | 特征提取与批量评测，并行调参 |
| 三阶 | 引入 PatchCore | 1×GPU（24 GB 显存） | 良品特征常驻显存，多品类并行 |
| 四阶 | 视觉语言模型复核 | 1–2×GPU 或云端 API | 仅对低置信度件二次复核 |

原则是分级投入、按需扩容，日常判定留在 CPU 侧，GPU 只用于训练、批量评测与疑难件复核。若接入大模型，建议级联架构——感知层先以毫秒级代价筛出可疑件（通常 20% 以内），仅对其调用大模型，可将推理成本压到全量调用的五分之一以下。

改用 PatchCore 时，单品类需存约 200–500 张良品特征，四品类合计不足 20 MB，可全量常驻；若保留全量图像追溯，日产 10 万件将日增约 20 GB，建议缺陷件全存、良品抽存 1%。

## 八、开源与总结

项目已开源，含感知层、三智能体、优化闭环、对照实验、界面与课程文档；一条命令可复现全部指标，无需 GPU、外部数据集或密钥。作为工程实践，其价值不在于把指标刷多高——合成数据上的零漏检本不该过度解读——而在于验证了一条**把工艺经验写成提示词、再让系统自己校准提示词**的技术路径。

后续有三个方向，接入真实数据检验判据在光照与批次漂移下的可迁移性；把反思机制从单条边界反推升级为判据结构调整；引入人工复核形成人在回路的持续学习。工业质检的终局不是无人，而是人在关键处、机器在重复处，本实践希望为这一分工提供可运行、可审计、可持续改进的原型。
